03 / ProblemPattern: vibe-code → mass PR → rubber-stamp → prod regression
T/HQDiagnosisgreat power, great responsibility
why this keeps happening

Vibe-coding from zero is easy.
Touching what already exists is the hard part.

Greenfield with an agent → no priors, no constraints, no taste yet to violate. The agent looks brilliant.

Refactor / migrate an existing codebase → the agent must respect a thousand decisions it never made: ADRs, retry conventions, deploy policy, schema sign-offs, jest coverage floors, the why-this-was-2k-lines-and-not-200.

When unit tests pass on a vibe-coded source, the agent learns that the shape of the bypass is the way home. Tests stop being a contract; they become a permission slip.

With great power (coding agents) comes great responsibility — to ship at scale, in a codebase someone else has to maintain on Monday.

architect backend data science ui devops

Major revamps are a team sport. The fix isn't a smarter agent. It's an org structure the agent has to ask permission from.

05 / SolutionVolume I, Issue 005 · Acme Eng · decision feed
T/HQHow it worksthe loop

Trigger → Acceptance → Questions → Plans → Sandbox → Quorum → PR.

1 · Trigger

SDK upgrade, feature proposal, refactor, or migration. Source can be a webhook, cron, or a human in the UI.

2 · Acceptance Criteria

For new features the agent drafts definition of done first. Each criterion gets a team owner + a verifiable test command.

3 · Per-role Questions

Grounded in each lead's Hyperspell history (Slack, Notion, GitHub). Only the addressed user can answer; everyone else sees the citations.

4 · Per-team Plans

Synthesised against that team's brain (gpt-oss-120b via Hyperspell). Cited by ADR + Slack thread.

5 · Sandbox

Tensorlake firecracker microVM. Real network, real git + gh, ephemeral.

6 · Quorum gate

Default ON. PR cannot ship until every team lead approves their plan card.

7 · Real PR

Branch pushed via OAuth-scoped gh. Merge, comment, audit trail logged back to InsForge.

T/HQArchitecturethree runtimes · one decision feed

Three runtimes, one decision feed.

Vercel · Next.js

user-facing

App Router · Tailwind 4 · server actions for OAuth + scenario triggers · streams cards to the feed every 2 s.

Tensorlake · Agent

compute

Custom Image() w/ git + gh + python · @application + @function · firecracker sandbox at runtime · secrets via tl secrets.

InsForge · Backend

data plane

Postgres tables: orgs, org_members, teams, projects, runs, cards, oauth_tokens, audit_log · AI gateway for ranking + structured JSON.

Why split? Each runtime stays simple: web is stateless, agent is ephemeral, DB is the only durable surface. Failure of any one degrades cleanly.

Why MCP on top? The agent's chat history is durable in InsForge — any agent client can resume. Devin today, Claude Code tomorrow, Codex next week.
